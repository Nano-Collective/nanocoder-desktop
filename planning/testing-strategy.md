# Testing strategy

How each part of the plan is tested, the measurable targets results are judged against, and the cross-platform CI that runs them.

- Status: Draft
- Last updated: 2026-10-29
- Drafted by: @akramcodez

## Conventions

Decided ([Stack suggestions][stack]): AVA loaded through `tsx`, `.spec.ts` files beside the source they test, `serial: true` and `workerThreads: false`, c8 coverage with an 80% line floor and fail-on-drop, and `pnpm test:all` as the single gate.

## Test layers

| Layer | What it proves | Runs where | Runs when |
|---|---|---|---|
| Unit | Pure logic: parsers, policies, state machine, canonicalisation | AVA in Node, all three platforms | Every pull request |
| Main-process integration | Services against real files, real Git and a real SQLite file in a temporary directory | AVA, all three platforms | Every pull request |
| ACP integration | The ACP client against a real `nanocoder --acp` with a scripted provider | AVA, all three platforms | Every pull request |
| End to end | The built app driven through its UI | Playwright, against a test build with the `nodeCliInspect` fuse on, all three platforms | Every pull request to `main` once Milestone 1 starts |
| Shipped-build smoke | The shipped build starts, opens a project and exits, without an inspector; its fuses are set as `SEC-19` says | Script per platform | Every release candidate |
| Packaged runtime | On a machine without Node installed the packaged app runs a turn; the sidecar's fuses are off; an inherited `NODE_OPTIONS` runs no extra script | Script per platform | Every release candidate |
| Packaged | Installers on clean machines, real provider | Manual, then automated with a CI secret | Every release |

## Fixtures

Suggestion (not discussed). Kept under `test/fixtures/` and generated by scripts, because Git cannot store some of them (empty directories, links on Windows):

- **Path fixtures.** A project with a symlink to a sibling outside the root, a Windows junction, files whose names differ only by case, names with spaces, newlines, bidirectional-override characters and reserved Windows names, and a 20,000-entry directory.
- **Git fixtures.** Repositories with staged, unstaged, untracked, renamed, copied and deleted files; a binary change; a submodule; an in-progress merge; a detached `HEAD`; one with `core.fsmonitor`, an external diff driver and a text conversion filter configured, each pointing at a script that would create a marker file if run.
- **Session fixtures.** Recorded `initialize` responses from each supported Nanocoder version, and saved session files for replay tests.

## Unit-testable surfaces

| Service | What to test | Requirements |
|---|---|---|
| Path canonicalisation | Relative path rules, `..` escapes, symlinks and junctions out of the root, case-insensitive comparison, Unicode normalisation, Windows reserved names and stream syntax | `SEC-03`, `FILE-10` |
| Git status parser | NUL-delimited porcelain output: renames, copies, untracked, spaces and newlines in names, submodules | `GIT-02`, `GIT-04` |
| IPC validation | Every handler rejects malformed, oversized and unknown-field requests and wrong senders | `SEC-02` |
| ACP projection | Session updates to thread state, including replay, cancel, permission and failure | `CHAT-05`, `ACP-07` |
| Thread state machine | Every transition in [`architecture.md`](architecture.md#thread-state-machine), including a thread recorded as Running at launch | `DATA-02` |
| Capability gates | Gate results from recorded `initialize` responses for each supported version | `ACP-03`, `ACP-04` |
| stderr ring | Size bound, redaction patterns, no persistence | `ACP-16`, `SEC-08` |
| Browser broker policy | Origin rules, mode gate, sensitive-action classification | `BRW-03`, `BRW-13`, `BRW-16` |
| URL detection in terminal output | Localhost forms, ports, trailing punctuation, ANSI sequences | `TERM-05` |
| Migrations | Each migration from an empty and a previous database | `DATA-03` |

## Integration tests against `nanocoder --acp`

Spawn a real Nanocoder build with a scripted model provider, so tests are deterministic and need no API key. Nanocoder resolves providers from `agents.config.json` and accepts OpenAI-compatible endpoints, so a local stub server that replays scripted responses (text, tool calls, errors) can stand in for a model. Built in phase G.4 (`fixtures/scripted-provider.ts`): it answers requests that offer tools from a script, and anything else (a title, a summary) with a fixed reply.

Cases:

1. `initialize` returns the capabilities recorded for that version.
2. New session, prompt with plain text, `end_turn`.
3. Prompt that calls a protected tool; allow once; reject once.
4. Cancel during streaming, and during a pending permission.
5. `session/close`, then `session/resume` of the same ID.
6. End the process, start a new one, `session/resume`, follow-up prompt.
7. `session/resume` of an unknown ID fails.
8. Two sessions with different `cwd` values in one process run tools in their own directories.
9. An untrusted spawn directory exits with Nanocoder's message on stderr.

They live outside `ava.files` (their own pattern and script), so `pnpm test:ava` never needs Nanocoder. Until the next Nanocoder release, they run against a build of Nanocoder `main`, since published 1.31.0 lacks cases 5, 8 and 9 ([`acp-integration.md`](acp-integration.md#supported-nanocoder-versions)).

## Technical gate test

The scripted version of the gate in [`roadmap.md`](roadmap.md#technical-gate), run in CI on all three platforms, plus the manual provider-backed run.

## Interactive QA launcher

Run `pnpm build`, then `pnpm qa:launch`. The test-only launcher at `e2e/qa/launch.ts` uses the built app, a copied fake Nanocoder fixture, a separate profile and project under git-ignored `.qa/`, and Playwright-only native dialog stubs. It does not build or add hooks to shipped main-process code. It uses the built renderer even when a development-server environment variable is inherited.

Connect `agent-browser connect 9333`. The Chromium debugging endpoint is bound to `127.0.0.1`; confirm the listening address before use. Stop the printed launcher PID after QA. Keep screenshots and logs under `.qa/`, with fake-fixture data only, never real chat, tool output or stderr.

`tsconfig.e2e.json` checks the launcher, Knip discovers it through `qa:launch`, and Playwright's `*.e2e.ts` match does not run it as a test. Packaging includes `out/` and package metadata only, with explicit exclusions for `e2e/` and `.qa/`.

Workspace contract tests in `source/main/ipc/workspace.spec.ts` cover every added handler's malformed, unknown-field and wrong-sender refusals, unavailable services, and injected-service dispatch. They also refuse content in storage patches, renderer-selected paths, `yolo` defaults and untrusted start/restart intents. `e2e/app.e2e.ts` checks the real bridge, unavailable project actions, validation and data-only subscription teardown.

Phase 1.1 store tests in `source/main/store/store.spec.ts` use real temporary SQLite files in plain Node. They cover every numbered migration, previous-version backup, rollback, newer-version refusal, corruption quarantine, schema-wide privacy introspection, canonical paths, sidecar-link refusal, metadata queries and persistence. `e2e/store.e2e.ts` repeats persistence, migration backup and corrupt-file startup against Electron's bundled Node. `e2e/connect.e2e.ts` scans the database and sidecars after a fake conversation for prompt, agent and tool text. Every end-to-end launcher uses a separate temporary profile so tests never write the normal desktop store.

Store regressions also cover simultaneous previous-version opens with an event barrier, write-lock ownership before settings/UI reads, newer-but-corrupt schemas, metadata-only updates after a folder moves, mixed timestamp precision and stale runtime overrides. A native crashed-WAL fixture proves committed data reaches the quarantined database after close/checkpoint, without promising original WAL/SHM bytes. The built-app suite launches a second process for the same profile and checks its clean exit and the owner's window focus request. A macOS-only native regression closes the owner's last window, launches a second instance and waits for exactly one new window with working storage IPC. It skips other platforms, where the last window closing quits the app. Lifecycle unit tests prove early requests wait for store/IPC readiness, coalesce and cannot re-enter window creation. They also prove shutdown discards queued demand, ignores requests during asynchronous disposal and cannot be reversed by later readiness. A native quit regression dispatches controlled activation and second-instance events inside the real `will-quit`, confirms the closed windows stay closed and removes its temporary follow-up quit hold before cleanup. No fixed sleeps or production test hooks are used.

## Packaged restart-and-resume test

Required before release ([whitepaper, Resume sequence][wp-resume]). Protocol, per platform, on a packaged build and a machine that has never run the app:

1. Install, launch, add a real repository, trust it.
2. Start a thread with a real provider. Ask the model to remember a made-up code word and to edit one file.
3. Approve the edit.
4. Quit the app. Confirm no Nanocoder process remains.
5. Relaunch, open the same thread, and ask for the code word.
6. Pass when the answer contains the code word and the thread history matches what was shown before quitting.

Record the platform, app version, Nanocoder version and result in the release pull request.

## Performance targets

Suggestion (not discussed): starting budgets, to be confirmed after the first measurements in phase 4.8. Measured on a reference machine the NC core team agrees (proposed: 4 CPU cores, 8 GB RAM, SSD, the oldest supported OS version per platform).

| ID | Target | Measured how |
|---|---|---|
| PERF-01 | From launch to a usable project list: 3 seconds or less, not counting Nanocoder startup. | End-to-end timer, cold start, median of 5 runs. |
| PERF-02 | From spawn to `initialize` answered: recorded every release; investigate any run over 5 seconds. MCP server startup is recorded separately. | Supervisor timestamps. |
| PERF-03 | A resumed thread of 200 messages is usable within 2 seconds after replay ends. | End-to-end timer on a fixture session. |
| PERF-04 | While receiving 100 `session/update` notifications a second, input and scrolling respond within 100 ms. | Scripted provider plus event-loop and frame timing. |
| PERF-05 | A directory listing up to the entry cap (proposed 2,000) returns within 300 ms. | Service timer on the 20,000-entry fixture. |
| PERF-06 | Text files up to 1 MiB preview within 500 ms; larger files show metadata instead. | Service plus render timer. |
| PERF-07 | Git status returns, or returns `LIMIT`, within 5 seconds on a repository with 100,000 tracked files. | Service timer on a generated repository. |
| PERF-08 | A single-file diff up to 1 MiB returns within 1 second; larger diffs return `LIMIT`. | Service timer. |
| PERF-09 | Idle memory with one project open and no browser page is recorded every release; a rise of more than 20% blocks the release until explained. | OS process metrics. |
| PERF-10 | Installer size per platform is recorded every release, as the whitepaper asks ("measured, not defended"). | Release artefact sizes. |

## Accessibility targets

Behaviour only. Visual design: see [`DESIGN.md`](../DESIGN.md). The criteria named are from WCAG 2.2; Suggestion (not discussed) to adopt them.

| ID | Target | Checked how |
|---|---|---|
| A11Y-01 | Every action in the app can be done with the keyboard alone, with no keyboard traps; the terminal documents its escape key (WCAG 2.1.1, 2.1.2). | Keyboard-only run of every success item. |
| A11Y-02 | Focus order follows the reading order. A permission request takes focus and returns it where it was when answered (WCAG 2.4.3). | End-to-end test plus manual check. |
| A11Y-03 | Every control exposes a name, role and state to assistive technology (WCAG 4.1.2). | Automated accessibility-tree assertions in end-to-end tests. |
| A11Y-04 | Turn started, completed, failed, cancelled and "approval needed" are announced without moving focus (WCAG 4.1.3). | Screen-reader check. |
| A11Y-05 | Streaming text is announced at a polite rate, not chunk by chunk. | Screen-reader check during a long turn. |
| A11Y-06 | Each release, the main screen reader on each platform completes `SP-03`, `SP-04`, `SP-07` (file preview) and `SP-08` (diffs), since CodeMirror renders only the visible part of a document: VoiceOver on macOS, NVDA on Windows, Orca on Linux. Unverified: how well Orca works with Electron apps; the first run will show. | Manual protocol recorded in the release pull request. |

## Cross-platform CI

Decided in [#10](https://github.com/Nano-Collective/nanocoder-desktop/issues/10) ([picks](https://github.com/Nano-Collective/nanocoder-desktop/issues/10#issuecomment-6412197487), [review](https://github.com/Nano-Collective/nanocoder-desktop/issues/10#issuecomment-6415011518)). The shared `pr-checks` workflow runs on Linux only, with one Node version ([source][shared-prchecks]), so these jobs live in our caller, as Nanocoder's Windows jobs do ([source][nc-prchecks]):

| Job | Platforms | Runs on | Contents |
|---|---|---|---|
| Unit and main-process tests | `macos-latest`, `windows-latest`, each on Node 22 and 24 | Every pull request | The AVA suite, including the `node:sqlite` store specs on Node 24 |
| ACP integration | All three | Every pull request | Its own test pattern and script, outside `ava.files`, so the shared unit job never needs Nanocoder. Runs against a pinned Nanocoder `main` build, built in CI and cached, until the next Nanocoder release |
| Package smoke | Linux under Xvfb, `macos-latest` (arm64), `macos-15-intel` (x64), `windows-latest` | Pushes to `main`, and pull requests that touch packaging config | Build an unsigned installer, launch it, check it exits cleanly. Filtered by a job-level condition, never a workflow `paths:` filter, which would leave a required check pending |
| End to end | All three, Linux under Xvfb | Every pull request to `main`, and every push to it. Switched on in the technical gate, ahead of Milestone 1, because the IPC and UI glue is covered only by these tests | Playwright against a test build with the `nodeCliInspect` fuse on |

- **Required checks.** Only the six NC checks are required, as in Nanocoder. The local jobs start advisory; the unit jobs can become required once stable, which is the NC core team's call.
- **Actions** are pinned by commit SHA.
- **Nanocoder on macOS.** Nanocoder's own CI never builds on macOS, so the first macOS run of the ACP job shows whether its `main` build works there and whether caching is needed.
- **To check in phase S.4:** how long each job takes on macOS and Windows, and the flake rate over the first two weeks.

## Security tests

| Test | Requirement |
|---|---|
| Path traversal and symlink or junction escape through the file service and ACP reads | `SEC-03`, `ACP-11` |
| Malformed, oversized and wrong-sender IPC | `SEC-02` |
| App renderer cannot navigate, open windows or reach Node | `SEC-01`, `SEC-15` |
| Browser view has no preload and no IPC; permission, popup, protocol and upload requests are denied | `SEC-10`, `SEC-12` |
| Git calls never run a pager, external diff, text conversion or `core.fsmonitor` (marker file never created) | `SEC-06` |
| Launch refuses a runtime inside the project's own `node_modules` | `SEC-05` |
| Nothing from the ACP stream or stderr reaches disk (scan the app data directory after a turn for the code word) | `DATA-04`, `SEC-07` |
| `openExternal` is called only for allowed schemes after a user action | `SEC-16` |

## Coverage policy

80% lines with fail-on-drop for `source/main` and `source/shared`. Electron bootstrap and renderer entry files can be excluded, the way Nanocoder excludes its app entry ([source][nc-c8]). If the project starts below the floor, pin `coverage-threshold` just under current coverage, comment it with the tracking issue, and remove it at 80 ([Project infrastructure][infra]).

## Flaky tests

A test that fails without a code change is quarantined in a tracking issue within a day and fixed or deleted within a week. Tests never sleep for a fixed time; they wait for an event, as Nanocoder's own ACP tests do for title generation. Suggestion (not discussed).
